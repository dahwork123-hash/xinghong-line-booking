## 1. 建置結論

首版已同意採「LINE 按鈕預約 + 固定規則與核定罐頭 + 小型預約管理後台」。以簡單完成預約、不增加訂閱或平台月租為設計目標，先不接付費 AI API、不買客服外掛，不建新聊天收件匣。

求職者完成點選與基本資料後直接預約。主管在原 LINE 官方帳號後台處理人工聊天；新後台負責預約名單、場次人數、查詢、改期取消及設定。這是自動化預約，不等同可自由理解所有文字的生成式 AI 客服。

零新增平台費是需經測試驗證的目標，不是永久免費或無人維護的保證。正式上線仍需公司持有雲端帳號、登入權限、備份與故障處理窗口。

## 3. 九欄個資如何簡化

原本九欄是：姓名、性別、年齡、連絡電話、居住縣市／行政區、前一份工作內容、應徵縣市、收到應徵職務名稱、加入來源。

| 原欄位 | 已同意的首版安排 |
|---|---|
| 姓名 | 必填，自行輸入 |
| 連絡電話 | 必填，自行輸入並確認格式；未做簡訊驗證，不宣稱已驗證持有人 |
| 收到應徵職務名稱 | 必選，改為清楚的「應徵職務」按鈕 |
| 應徵縣市 | 必選，用按鈕選擇 |
| 加入來源 | 選填，可跳過；沒有可驗證來源時保留未知 |
| 性別、年齡 | 不作為預約必要欄位，首版不主動收集 |
| 居住縣市／行政區 | 不作為預約必要欄位；不能用來取代應徵縣市 |
| 前一份工作內容 | 不作為預約必要欄位，面試現場再填履歷 |

也就是「輸入姓名、電話 + 點選職務、縣市」四項必要資料。面試分公司、日期、時間由接下來的點選產生；LINE 身分、預約編號與異動時間由系統產生，不另要求求職者填寫。

沿用舊格式貼資料的人仍可進入流程：用欄位標籤解析，只取預約必要資訊；缺哪一項就補問哪一項。辨識不確定時請本人重新點選，不用付費 AI 猜測。不要把範例姓名或電話當成完成資料，也不在新預約主檔額外留存完整九欄原文。

原 LINE 後台既有歡迎訊息本輪不更動。四欄流程可先從新增的「預約面試」入口使用；未來是否同步精簡歡迎訊息，先提供文案再由使用者核准。

## 4. 求職者操作流程

1. 點人力銀行上的既有 LINE 連結，加入或開啟 `@064lhzfu`。
2. 從選單或傳送「預約面試」進入；舊好友不用重新加入。
3. 點應徵職務、應徵縣市；南投再選到台中或彰化面試。
4. 輸入姓名、電話，顯示基本資料供本人核對；來源可略過。
5. 點具體日期，再選該日尚有名額、未截止、未停辦的時間。
6. 顯示完整摘要：職務、分公司、年月日、時間、地址、姓名電話。
7. 按「確認預約」後，由後端重新檢查容量、時間及重複預約；資料庫寫入成功才回覆成功。
8. 收到預約編號與入場資訊。行政提醒找 TOBY；其他職務沿用核定分公司確認文案。
9. 可從「我的預約」查詢、申請改期或取消；非標準問題選「聯絡招募人員」。

預約成功文案含入場方式、自備原子筆、團體面試與停辦說明。時間及地址由場次資料帶入，不能讓文字罐頭和實際預約各有一套日期。

首版以聊天室互動為主。已核定的 FAQ 可透過按鈕或明確關鍵字回覆；複雜敘述、含糊日期及未核定問題交由人工。問「只有四點嗎？」不是確認預約。

## 6. 管理後台範圍

新後台是一個登入後的管理網頁，不是直接把功能新增到 LINE 原生後台。兩個後台分工清楚：新後台管理預約，LINE 原後台人工聊天。

| 頁面 | 首版內容 |
|---|---|
| 場次總覽 | 依面試日期看全區、分公司、場次；顯示一般／行政各組的新系統已約數、剩餘數；點數字進名單。明示不含未登錄的人工預約 |
| 預約查詢 | 依姓名、電話、職務、應徵地、面試地、面試日期、狀態查詢；明列預約編號 |
| 預約明細 | 聯絡資料、確認資訊、改期取消歷程、處理同仁、必要內部備註 |
| 時段設定 | 每週排程、分組容量、14 天範圍、提前 1 小時截止、臨時停開、加場、生效日期 |
| 罐頭管理 | 依職務／地區分類，草稿、預覽、發布；保留版本及操作者 |
| 匯出 | 匯出目前篩選結果為真正 `.xlsx`；不匯出 LINE 身分憑證、登入資訊或不必要個資 |
| 人工處理狀態 | 待人工、人工接手、恢復自動；記錄操作同仁及時間，接手後暫停該人的自動回覆；不提供新的人工聊天輸入框 |

所有獲授權同仁都看全區、操作全部首版功能，包含設定發布、預約代操作、匯出及停辦。首版不設主管／同仁權限分級，但仍須登入、每人獨立身分，操作記錄保留人員及時間。「全部同仁可操作」不等於公開免登入，也不需要共用 LINE 或雲端密碼。

時段與機器人罐頭在新後台統一控制。若主管仍使用 LINE 原生「預設訊息」，首版不承諾兩邊罐頭自動同步；新後台提供核定文字供複製，避免不同版本。原生歡迎訊息仍由原 LINE 後台負責，避免雙重發送。

### 統計口徑

| 指標 | 資料及計算 | 排除／界線 |
|---|---|---|
| 新系統有效預約數 | 按面試日期、場次與分組，計算目前有效的唯一預約 | 排除取消及已改到其他場的舊歸屬；重送不加一 |
| 場次已占名額 | 僅等於新系統有效預約數，不加交接保留名額 | 不含未登錄的人工預約，不能稱為該場實際全部預約人數 |
| 全區／分公司合計 | 相同篩選下逐場逐組加總 | 稱為預約人次；跨期間去重人數另算，不混稱 |

總覽、名單及匯出共用同一組篩選條件；面試日期和建立日期分開。正式首版不計到場、未到及到場率，也不把超過面試時間的人自動標成未到。

## 7. 原 LINE 後台人工回覆如何協作

人工接手操作已核定：新後台按「人工接手」→ 回原 LINE 聊天 → 處理完按「恢復自動」。這是已確認的建置需求，目前尚未串接正式服務。

1. 求職者要求人工或系統無法處理時，保存待人工狀態並暫停該人的一般自動對話。
2. 同仁在新後台按「人工接手」，系統保存操作人員及時間，暫停該人的自動回覆，再回原 LINE 後台聊天；不假設機器人能自動偵測每一次主管發話。
3. 若要讓人工協助的預約出現在新後台，先用新後台代約並成功占額，再回 LINE 確認；此路徑仍受每組 5 人限制。若是原 LINE 或現場另行安排、未登錄系統的人工預約，不列入系統名額及查詢人數，現場合計超額可接受。
4. 處理完後明確按「恢復自動」，才恢復該人的自動對話。首版不設自動解除時限，不因收到下一則自由文字就自行恢復。
5. 本人可查詢既有預約；人工接手期間是否允許自助異動需有一致規則，建議異動也交接手主管處理。

新系統保存完整的新預約異動紀錄，但不承諾自動複製原 LINE 後台所有人工聊天。這是根據標準 Webhook 事件範圍作的整合邊界判斷，原生人工發話同步需另外驗證。正式上線前要實測原 LINE 聊天與 Webhook 的設定共存、歡迎訊息不重複，以及人工接手後自動回覆確實停止。[LINE 接收訊息與 Webhook](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)

## 8. 不搬舊資料的上線交接

不匯入舊姓名、電話、履歷或聊天。上線後的新預約才建立主檔；上線前已約好的對象仍在原 LINE 管理。

使用者已確認沿用名額解讀，不改成不限人數：不要求提供舊場次人數、不建立交接保留名額；新系統仍按每組 5 人限制，加上人工預約後現場合計超過人數可接受。

例如舊人工或系統外另約 3 人，新系統仍可收 5 人，現場合計可能 8 人；不能因此讓第 6 人在新系統自助預約成功。系統內代約按正常名額處理，不另增加超額補登功能。

上線前舊約及未登錄的人工另約，其改期取消仍回原 LINE 處理，不新增舊名單或保留名額欄位。後台人數及匯出明示「新系統預約紀錄，不含未登錄的人工預約」，不保證等於現場總人數；也不要求等待舊約全部結束才能上線。

### 現有 AI 訂閱能做什麼

ChatGPT Pro 與 OpenAI API 分開計費，Pro 不包含此 LINE 應用的 API 用量。Claude Max 訂閱也不包含 Claude API。既有訂閱可依各自方案使用開發工具協助製作與維護，不能直接視為對外 LINE 機器人的免費 API 額度。[OpenAI 官方計費說明](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform)、[Claude 官方訂閱與 API 說明](https://support.claude.com/en/articles/9876003-i-have-a-paid-claude-subscription-pro-max-team-or-enterprise-plans-why-do-i-have-to-pay-separately-to-use-the-claude-api-and-console)

首版建議不呼叫 AI API，故該項用量為 0；並非以自動操作 ChatGPT／Claude 網頁或挪用訂閱登入憑證當成機器人 API。需要自由文字理解時，再提出可選 API 方案、估算用量與費用上限，核准後才接。

| 即時互動回覆 | 候選人送出訊息／Postback 後即時用 Reply API 回應 | 不能把延遲提醒、後端主動通知也當成免費 Reply |
| AI 模型 | 不接生成式 AI API，API 費 0 | 未來選配 OpenAI／Claude API，另依用量計費 |
| 主機及資料庫 | 先評估 Cloudflare Workers Free + D1 Free | 超額、CPU 等限制不符實測、需要升級；Workers 付費方案最低 US$5／月，另有超量費 |
| 網址 | 測試可先用供應商提供的網址 | 正式建議公司既有網域的子網域；沒有既有網域時可能有網域年費 |
| 客服外掛、簡訊、提醒 | 首版不購買、不提供 SMS 驗證、不啟用排程提醒 | 日後購買第三方預約工具、發簡訊或啟用主動提醒 |
| 開發及維護 | 在現有開發工具訂閱額度內協作，不另採購平台 | 超額工具點數、外包、代維護、備份儲存或付費監控；故障處理仍需人力 |

LINE 的 Reply API 不計入月訊息額度，Push／群發等會計入。原 LINE 後台的一對一聊天也是免付費訊息；不能把主管在原後台的延遲聊天，誤說成必定使用付費 Push。[LINE Messaging API 計費](https://developers.line.biz/en/docs/messaging-api/pricing/)、[台灣官方方案及免付費訊息](https://tw.linebiz.com/column/LINEOA-2026-Price-Plan/)

因此，首版最後確認放在聊天室按鈕，利用當次事件即時回覆。若日後改用網頁短表單，表單送出後由伺服器主動發 LINE 成功通知，通常須另評估 Push，不直接套用同一零訊息費假設。Reply 的時效與一次性使用限制仍須在串接時驗證；重試失敗不能默默改用付費 Push。

台灣輕用量每月含 200 則計量訊息。中用量目前未稅 800 元／月、含 3,000 則；已公告 2026-11-01 改為未稅 1,000 元。高用量目前未稅 1,200 元、含 6,000 則，11/1 改 1,400 元。首版不預設要升級。假設每月有 300 人完成預約、每人主動推播一次提醒，即為 300 則，已超過輕用量 200 則；每日來訊 10～20 人不能直接推定都有預約或都要付費。[台灣 LINE 官方公告](https://tw.linebiz.com/column/LINEOA-2026-Price-Plan/)

Cloudflare 現行免費額度包括 Workers 每日 100,000 次請求；D1 每日讀取 500 萬列、寫入 100,000 列、總儲存 5 GB。依本案 10～20 位來訊及 2～3 位同仁推估，適合作為低費用測試起點；仍需實測 CPU、索引、登入、備份及其他同帳號服務共用額度，不能只看人數保證足夠。免費額度用盡可能服務失敗，不是保證自動免費擴容。[Workers 價格](https://developers.cloudflare.com/workers/platform/pricing/)、[D1 價格及超額行為](https://developers.cloudflare.com/d1/platform/pricing/)

Cloudflare 官方建議正式用途使用自有網域或路由，而非將 `workers.dev` 作為業務關鍵服務網址。測試可不買網域，正式上線前先查公司是否已有可用子網域。[workers.dev 使用限制](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/)

費用防線：不啟用付費 AI、不升級付費主機、不購買外掛、不自動充值；不影響既有其他系統的帳務設定。正式測試核對登入及備份是否會另收費。免費方案接近限制時由同仁決定縮減使用或核准升級，系統故障不得回覆「預約成功」。

## 10. 正式架構與安全底線

`LINE 訊息／按鈕 → 簽章驗證 Webhook → 規則及預約服務 → 持久資料庫 → 即時 Reply`

`同仁登入的預約後台 → 同一預約服務與資料庫`

建議先以 Cloudflare Workers + D1 驗證低用量方案；不是已部署或已完成容量測試。資料庫是人數與預約唯一依據，Google Sheet 不作為名額鎖定主檔，也不要求另外建立表單。

必備：LINE 簽章驗證、事件去重、同人重複預約防護、資料庫原子名額操作、並發改期測試、過期按鈕驗證、管理者登入白名單、個資查詢授權、敏感資訊不進前端、備份還原及發送結果紀錄。查詢自己的預約須驗證 LINE 身分，不能只知道姓名電話就看到他人資料。

只保留必要預約資料與異動事件；未完成預約的對話狀態短期保存，完整聊天備份不是首版功能。預設保存 1 年已確認；實作按該筆面試日期起算 1 個曆年，改期採最後確認的面試日期，取消採原定日期。這是保存規則的實作口徑，不宣稱為法定期限。

到期清除該筆可識別個資及關聯備註時，不連帶刪除同一人其他尚在保存期的預約。個資用途告知、聯絡窗口、備份與匯出檔的到期處理在正式上線前落實；本輪沒有執行資料刪除。測試一律用虛構姓名電話。
